What I learned

Describe your design: hypervisors, tenants, VNIs and addresses. Which tenants overlap, and why did you place each VM where you did?

My underlay network is 10.8.0.0/24, with three hypervisors, hv1 (.1), hv2 (.2) and hv3 (.3). Tenant red uses VNI 100 and has VMs on all three hypervisors. Tenant blue uses VNI 200 and has VMs on hv1 and hv3. Both tenants use the same network (10.8.50.0/24), so their addresses overlap on purpose. I put red on all three hypervisors so it can demonstrate the broadcast can reach a hypervisor that is not part of the conversation. hv1 and hv3 each host one red VM and one blue VM, so two tenants share one machine and I can test that they stay seperate

Two of your VMs have the same IP address. Using your evidence, explain how a ping reaches the right one â€” and what would have to go wrong for one tenant to see another's traffic.

red1 and blue1 both ping 10.8.50.11, but the answers came from different VMs. In isolation.txt, red1 learned the MAC 02:00:00:64:00:0b for that address, and blue1 learned 02:00:00:c8:00:0b. The middle of each MAC is the tenant's VNI, 0x64 is 100 for red and 0xc8 is 200 for blue, so red1 was answered by red2 and blue1 by blue2. While red1 pinged, tcpdump on blue2 captured 0 packets, because the traffic carried VNI 100 and hv3 delivers it only into red's bridge. For one tenant to see another's traffic, something would have to break the VNI separation, like maybe two tenants given the same VNI, a VM plugged into the wrong tenant's bridge, or a VXLAN device with the wrong id.

Using your evidence, explain what was flooded, to which hypervisors, and what each VTEP learned. With 50 hypervisors in one VNI, how many copies would one broadcast need â€” and how would EVPN change that?

When red1 asked who has 10.8.50.11, that ARP broadcast was flooded by hv1 to both other hypervisors in red's flood list, hv2 and hv3. The capture on hv3 shows a VXLAN packet from 10.8.0.1 to 10.8.0.3 with VNI 100 carrying the ARP request, even though the ping was between hv1 and hv2. Afterwards hv1 had learned red2's MAC behind hv2 (10.8.0.2), from the reply. hv3 had learned red1's MAC behind hv1 (10.8.0.1), from the flooded request, but nothing about red2, because the reply went straight back to hv1. The later pings were unicast, so nothing more was copied to hv3. With 50 hypervisors in one VNI, one broadcast will have 49 copies, one for each hypervisor except the sender itself. It do VTEPs share where each MAC and IP lives through BGP in advance, so they can send traffic directly and answer many ARP requests locally, without flooding.

Compare your two MTU fixes using your measurements. Which would you choose for a data centre, what does each cost, and who has to change what?

Without a fix, a 1500-byte tenant packet needs 1550 bytes with the VXLAN header, so it does not fit the 1500-byte underlay and iperf3 moved 0 bytes. Fix A lowers the tenant MTU to 1450, and the largest ping that worked was 1422 (1450 bytes with headers) and iperf3 moved 922 MBytes. Fix B raises the underlay MTU to 9000 and keeps tenants at 1500, and the largest ping that worked was 1472 and iperf3 moved 979 MBytes. Both work, and the small speed difference in my simulation. Fix A costs nothing on the underlay, but every tenant VM has to be set to 1450, so the tenants (or whoever builds their VMs) must change, and every packet carries about 50 bytes less data. Fix B leaves tenants alone, but the network team must set 9000 on every underlay interface and switch port on every path, and one device left at 1500 brings the black hole back. For a data centre I would choose fix A when I cannot guarantee that every underlay device supports jumbo frames. It needs no change to the underlay, and a single switch left at 1500 cannot cause the black hole, because tenants never send more than 1450.

If your hypervisors' VTEPs were P4 switches running the lecture's vtep.p4, what would have to fill the vtep_encap table, and how? What would replace flood-and-learn?

A controller would have to fill the vtep_encap table, using P4Runtime. Each entry would say that traffic for a given VNI and destination goes to a given remote VTEP IP. The controller knows where each VM is placed, so it can write these entries as VMs are created or moved. This replaces flood-and-learn because the P4 switches no longer need to discover VM locations by flooding traffic and learning from incoming packets. Instead, the controller already knows the VM locations and provides the forwarding information to the switches. This is similar to EVPN, where BGP distributes MAC-to-VTEP information, but here the controller uses P4Runtime to install the entries.
